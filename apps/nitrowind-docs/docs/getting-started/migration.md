# Migration Notes

Nitrowind keeps the familiar React Native Tailwind shape: `className`, `global.css`, a Metro plugin, styled components, and `cssInterop` for third-party components.

Start with the read-only checker. It detects packages, Metro wrappers, the old
NativeWind Babel plugin, and Tailwind v4 CSS setup without editing files:

```sh
yarn nitrowind migrate --from nativewind
# or
yarn nitrowind migrate --from uniwind
```

## From NativeWind

Replace the Babel and Metro setup with the Nitrowind Metro plugin:

```diff title="metro.config.js"
- const { withNativeWind } = require("nativewind/metro");
+ const { withNitrowindMetroConfig } = require("@nitrofoundation/nitrowind/metro");

- module.exports = withNativeWind(config, { input: "./global.css" });
+ module.exports = withNitrowindMetroConfig(config, { input: "./global.css" });
```

Then import components and helpers from Nitrowind:

```tsx
import { NitrowindProvider, View, Text, cssInterop } from "@nitrofoundation/nitrowind";
```

Most utility classes stay familiar because Tailwind v4 still owns utility generation. Differences to check:

- No Babel plugin is needed.
- Native engine updates are designed around Fabric and React Native `0.86`.
- Platform, safe-area, group, and animation helpers are generated by the Nitrowind pipeline.
- Unsupported web-only CSS selectors are ignored or skipped when React Native cannot represent them.

## From Uniwind

The high-level workflow is similar: import Tailwind in CSS, wrap Metro, and use className. Nitrowind exposes both Tailwind and plain-CSS entry points, and the native engine is fully open source through `nitrocss`.

After either migration, rebuild the native application. NitroWind contains a
native module and therefore cannot be tested inside Expo Go.

## Historical Nitrowind aliases

The wrapper re-exports the full `nitrocss` runtime and keeps aliases:

| Alias | Actual export |
| --- | --- |
| `NitrowindProvider` | `NitroCssProvider` |
| `useNitrowind` | `useNitroCss` |
| `withNitrowind` | `withNitroCss` |
