# Replacing `culori` with native C++ color handling

**Verdict: possible — but the winning move is not a native binding.** The repo already owns a C++
parser with byte-for-byte culori parity ([cpp/css/CssColor.cpp](../packages/nitro-css/cpp/css/CssColor.cpp),
~1,100 lines, 53-case parity suite in [cpptests/css_color_test.cpp](../packages/nitro-css/cpptests/css_color_test.cpp)).
The question is only how the **build-time** compiler (which runs inside Metro's Node workers) and the
**on-device JS paths** get color parsing without the `culori` npm dependency. Perf is a non-issue
either way — measured cost of culori is ~0.8 µs per color, 0.4 ms per 500 colors, and a one-time
~4 ms `require` per Metro worker. Any migration is about **dependency hygiene and single-source-of-truth
parity**, not speed.

## Where culori is used today (audit)

Only three files import it, and only three symbols — `parse`, `formatHex`, `formatHex8`:

| Call site | Purpose | Needs |
|---|---|---|
| `src/compiler/toRNValue.ts:145–148, 233–237` | Lower any color value / theme variable to hex6/hex8 | parse → hex, alpha<1 rule |
| `src/compiler/parsers/gradient.ts:82–84` | Lower literal gradient stop colors | same |
| `src/compiler/parsers/boxShadow.ts:84–92, 147–153, 214–221` | Split shadow color into hex6 + **unquantized** `shadowOpacity` float | parse → hex **plus raw alpha** |

Critical wrinkle: culori is **not build-time-only**. `core/store.ts:277` calls `toRNValue` on-device
(first-paint + JS-fallback resolution), and `core/normalize.ts` imports `gradient.ts`/`boxShadow.ts`,
so culori is bundled into the app today. Any replacement that only works in Node (napi) breaks the
RN bundle unless these runtime-reachable modules are also weaned off it.

What the C++ engine already does at resolve time: `NitroCssEngine.cpp:171–177, 700–707` re-parses
color functions after `var()` substitution via `css::parseColorToHex` — the in-engine comments
explicitly anticipate a future "JS emits raw CSS" flip.

## Options evaluated

| Option | Feasible? | Effort | Verdict |
|---|---|---|---|
| **A. N-API addon** of CssColor.cpp (lightningcss/oxide pattern) | Yes | ~50-line binding, but 7–11-platform prebuild CI matrix + npm `optionalDependencies` install failures (the tailwind-oxide headline bug) | **Reject** — highest maintenance for zero perf need; no RN styling lib ships a napi addon for color alone |
| **B. WASM** (emscripten, `-sSINGLE_FILE -sMODULARIZE`, sync require in Metro workers) | Yes — ~30–100 KB artifact, one binary for all platforms | 2–4 days + owning an emscripten toolchain | **Viable runner-up** — the only true "same C++ bytes everywhere" route; choose only if structural parity is valued over toolchain simplicity |
| **C. Small pure-TS port** (~300–500 lines mirroring CssColor.cpp, shared golden test vectors) | Yes | 1–2 days | **Recommended** — see below |
| **D. Defer-to-native** (artifact ships raw color strings; only the in-app engine parses) | Partially | — | **Reject as full replacement** — loses build-time diagnostics, breaks web (react-native-web can't parse oklch/lab), breaks the JS-fallback path, and `shadowOpacity` needs a parsed alpha at compile time. Keep it as the existing safety net for runtime-injected themes only |
| **E. Adopt the ColorM C++ lib** (github soreja/colorm) | No point | — | **Reject** — dead since Jan 2023 (5 commits, 29 stars), weaker than the in-repo CssColor.cpp (no culori-parity contract, no color() audit, no test suite), and it doesn't solve the Node-execution problem anyway |

Ecosystem check: NativeWind v5 moved *away* from native (lightningcss) to pure-JS colorjs.io;
Tamagui vendors a tiny JS color normalizer; Unistyles parses colors in C++ **at runtime** but keeps
its build side in JS. Nobody ships a napi color addon.

## Recommended plan (Option C + engine-side lean)

The insight from the audit: **the "duplication" already exists** — CssColor.cpp is a hand-maintained
mirror of culori. A small TS port doesn't add a second source of truth; it replaces a third-party
moving target with a mirror we control, and parity becomes *mechanically enforced* by shared fixtures
instead of comment-enforced.

1. **Extract golden vectors.** Turn the 53 cases in `cpptests/css_color_test.cpp` into a shared JSON
   fixture (`packages/nitro-css/test/fixtures/color-parity.json`), generated by one script. Extend with
   the Tailwind v4 oklch palette (the real-world input source — Tailwind's default palette is oklch).
2. **Write `src/compiler/colors.ts`** (~300–500 lines): `parseColorToHex(css): string | null` +
   `parseColorParts(css): { hex: string; alpha: number } | null` (unquantized alpha for `shadowOpacity`),
   porting CssColor.cpp's grammar exactly (hex/named/rgb/hsl/hwb/oklch/oklab/lab/lch/color(srgb|srgb-linear|display-p3);
   reject color-mix/currentColor/relative/rec2020 — same as C++).
3. **Swap the 6 call sites** in `toRNValue.ts`, `gradient.ts`, `boxShadow.ts`; drop `culori` +
   `@types/culori` from package.json. The RN bundle shrinks (culori is 1.5 MB on disk) and the
   runtime paths (`store.ts`, `normalize.ts`) keep working unchanged.
4. **Wire the fixture into both suites**: vitest runs every vector through `colors.ts`; the C++ test
   reads the same JSON (or a generated header). One fixture, two parsers, drift impossible.
   Also add the currently-missing JS oklch-through-`toRNValue` test.
5. **C++ addition (small):** expose `parseColorParts`-equivalent (raw alpha is already computed
   internally at `CssColor.cpp:1058–1070`) so the engine and TS agree on `shadowOpacity` exactly.
6. **Optional follow-up (cheap win at runtime):** since compile output is always hex, the on-device
   JS path only ever re-parses hex — the TS port can fast-path that, and anything exotic at runtime
   is already covered by the engine's `lowerColorFunctionValue` safety net.

### If "C++ everywhere" is a hard requirement later
Do Option B on top of step 1: compile `CssColor.cpp` to a single-file sync WASM module and load it in
`colors.ts` behind the same two-function API, keeping the TS port as fallback. The API seam from step 2
makes this a drop-in swap.

## Risks
- TS port grammar drift → mitigated by the shared golden fixture (step 4) being the *only* spec.
- `shadowOpacity` rounding parity (0.35 vs 89/255) → covered by `parseColorParts` returning raw alpha on both sides.
- Exotic spaces culori parses but CssColor rejects (`color(rec2020 …)`, xyz) silently change from
  "lowered at build time" to "passthrough → dropped by RN". No repo CSS uses them; document as unsupported.
